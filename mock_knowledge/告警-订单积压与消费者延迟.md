# 订单积压与消费者延迟告警处理手册

## 告警名称

ORDER-CONSUMER-LAG-HIGH

## 适用范围

适用于订单消息队列消费延迟超过阈值的场景，包括订单创建后库存未锁定、支付后订单状态未推进、履约单未生成等问题。

## 告警触发条件

- 指标：`kafka_consumer_group_lag{group="order-worker"}`
- 触发：任一核心 topic lag 大于 50000，持续 10 分钟
- 严重级别：P1 或 P2，取决于是否影响支付后履约
- 核心 topic：`order.created`、`payment.succeeded`、`fulfillment.requested`

## 首要确认

1. 确认 lag 是否集中在单个分区。如果集中在单分区，优先排查热点订单或 poison message。
2. 查看消费者实例数和 rebalance 频率。
3. 查看 worker 日志是否出现反复处理同一 message key。
4. 查看数据库写入延迟和锁等待。

## 排查命令

```bash
kafka-consumer-groups --bootstrap-server kafka:9092 --describe --group order-worker
kubectl -n prod logs deploy/order-worker --since=30m | grep -E "retry|dead letter|duplicate key|lock wait|panic"
kubectl -n prod top pod -l app=order-worker
```

## 常见原因

- 单条异常消息反复重试，阻塞同分区后续消息。
- 下游库存服务限流，订单 worker 进入指数退避。
- 数据库慢查询导致单条消息处理耗时从毫秒级变为秒级。
- 消费者扩容后频繁 rebalance，实际消费时间下降。
- 新版本引入同步调用 CRM 或优惠券服务，放大链路耗时。

## 处置步骤

1. 如果存在 poison message，将该 message key 写入临时跳过名单，并把原始消息转储到 dead-letter topic。
2. 如果是下游限流，降低 worker 并发，保护下游服务，同时开启补偿任务。
3. 如果是数据库锁等待，先定位锁源事务，必要时终止长事务。
4. 如果 worker CPU 饱和，水平扩容，但确认 topic 分区数足够支撑扩容。
5. 如果 lag 超过 30 万且持续增长，升级为 P1，并通知交易、履约、客服团队。

## 恢复验证

- lag 连续 15 分钟下降，且没有新的 dead-letter 激增。
- 订单状态推进延迟 P95 小于 60 秒。
- 支付成功订单均能在 2 分钟内生成履约单。

## 注意事项

不要直接清空 topic。任何跳过消息必须记录 message key、offset、topic、处理人和恢复计划。
