# 数据库连接池耗尽告警处理手册

## 告警名称

DB-CONNECTION-POOL-EXHAUSTED

## 适用范围

适用于核心服务数据库连接池达到上限，导致接口超时、事务堆积、错误中出现 `too many connections`、`connection timeout`、`pool exhausted` 的场景。

## 告警触发条件

- 指标：`db_pool_in_use / db_pool_max`
- 触发：连接池使用率大于 90%，持续 5 分钟
- 严重级别：P1
- 重点服务：`order-service`、`payment-gateway`、`inventory-service`、`user-service`

## 首要确认

1. 判断是单服务连接池耗尽，还是数据库实例连接数打满。
2. 查看最近是否有慢查询、批处理任务、报表查询上线。
3. 查看连接是否泄漏，是否大量连接长时间 idle in transaction。
4. 查看数据库 CPU、IO、锁等待。

## 排查 SQL

```sql
select state, count(*)
from pg_stat_activity
where datname = 'biz_prod'
group by state;

select pid, usename, application_name, state, wait_event_type, now() - query_start as age, query
from pg_stat_activity
where state <> 'idle'
order by age desc
limit 20;
```

## 常见原因

- 新接口忘记关闭 rows 或事务。
- 批处理任务并发过高，占满连接。
- 慢 SQL 导致连接占用时间过长。
- 读流量没有走只读库。
- 服务扩容后每个实例连接池上限未同步下调。

## 处置步骤

1. 如果数据库实例连接数已满，先限流非核心接口和报表任务。
2. 终止超过 10 分钟且确认安全的只读慢查询。
3. 将读流量切到只读实例，并下调写库连接池上限。
4. 如果是新版本连接泄漏，立即回滚。
5. 对批处理任务降低并发，并设置连接获取超时。

## 恢复验证

- 数据库连接数低于实例上限的 70%。
- 服务连接池等待时间 P95 小于 50ms。
- 核心接口 5xx 和超时恢复到基线。
- 没有新的 idle in transaction 长事务。

## 禁止操作

不要盲目增加所有服务连接池上限。这通常会把问题从应用侧转移到数据库侧，并导致雪崩。
